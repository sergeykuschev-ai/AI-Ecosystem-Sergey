# Arthur Agent Harness — архитектура и этапы

## Среда и границы ответственности
- Основной сервер: Windows Amursk `DESKTOP-6NKDIC8` (Docker, API, PostgreSQL, Ollama).
- `stores-web1` — только SSH-мост/репозиторий для разработки; туда не переносить рабочие секреты, память, БД или KPI.
- Публичные каналы: Telegram и в дальнейшем голос/веб. Один оркестратор и один набор контрактов инструментов.

## Поток выполнения
1. **Ingress + Identity**: верификация Telegram user ID / доверенного канала, correlationId, ограничения частоты.
2. **Intent / Planner**: детерминированные намерения имеют приоритет. Планы, построенные LLM, **только read-only**, проверяются по whitelist навыков, операций, зависимостей и тайм-аутов.
3. **Policy Gate**: проверка ролей, `readOnly`, согласований, запрет непредусмотренных побочных действий. Записи без полномочий не запускать.
4. **Execution DAG**: независимые операции выполняются с жёстким лимитом параллелизма, зависимые — только после **success** prerequisite. При ошибке зависимый шаг помечается `skipped`.
5. **Verification**: подтверждение результата через skill contract; для записи в бизнес-систему — read-after-write либо server-generated operation ID. Не выдавать «выполнено» до подтверждения.
6. **State + Audit**: PostgreSQL, requestId, idempotency key, состояние выполнения, метрики latency/ошибок/количества вызовов, без токенов и чувствительного текста.
7. **Response + Monitoring**: человеку выдаётся статус `success | partial | failed` и причины; важные сбои — уведомление. Никаких выдуманных KPI.

## Модели
- `deepseek-flash` — ежедневные ответы и недорогая маршрутизация.
- `glm-5.3` — явно выбранные сложные задачи и код.
- `qwen2.5:3b` Ollama — fallback, если API недоступен или исчерпан внутренний лимит.
- Подключение и учёт резервируемых затрат через уже развернутый `paid_ai_budget`; это **не гарантированный потолок провайдерских списаний**.

## Статус на 2026-10-09
### v1: выполнено, задеплоено на Amursk
- Исправлена конкурентность (до 5, реально одновременно запускаемых, не заранее созданных Promise).
- После ошибки prerequisite не запускать зависимые действия. Отчёт `partial/failed`, со статусом `skipped`.
- Не делать повторов `readOnly=false` после неопределённого исхода/тайм-аута; у read-only максимум два повтора.
- Проверка дублей ID, циклов, отсутствующих зависимостей.
- Изолированные mock tests: 27/27, Windows 7/7, production-container tests: 7/7; отдельные Telegram client + business KPI tests: 26/26.
- Docker `arthur-core-telegram-gateway:harness-v1-20261009`, `healthy`, конфигурация Compose закреплена в локальном `compose.override.yml`; старый образ и rollback-override сохранены.

### Следующий этап (ещё не сделано)
1. **E2E Telegram**: нужен настоящий входящий запрос от авторизованного пользователя и подтверждённый исходящий ответ после релиза. Не использовать параллельно `getUpdates` с live bot (конфликт long polling).
2. **Подтверждения опасных действий**: `waiting_approval`, TTL, кто согласовал, точное действие и параметры, запрет исполнения без approval.
3. **Надёжная идемпотентность записей**: закреплённый `idempotencyKey`, дедупликация между рестартами и Telegram redelivery в Core API/PostgreSQL. Тайм-аут внешнего API означает `outcome_unknown`, а не «не сделано».
4. **Postcondition verification**: read-after-write и отчёт о результатах, а не обещание выполнения.
5. **Журнал и восстановление**: append-only аудит `planned / running / waiting_approval / verified / failed / needs_attention`; при перезапуске не повторять записи.
6. **Мониторинг**: метрики сбоя Telegram, KPI недоступен, зависших задач, возврат на Ollama, лимитов и занятости диска; тест rollback раз в релиз.

## Safety
Не хранить API-ключи в Git/отчётах/Telegram, не снимать защиту бюджетных файлов, не запускать shell/SQL через LLM план, не обходить блокировки удалённых инструментов, не менять базу 1С без отдельного согласованного контракта.
