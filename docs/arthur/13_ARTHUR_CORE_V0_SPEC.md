# Arthur Core v0 — техническая спецификация

**Статус:** утверждённая спецификация первого рабочего ядра  
**Версия:** 0.1  
**Дата:** 2026-07-29

## 1. Цель v0

Arthur Core v0 создаёт минимальное, но расширяемое ядро единого ассистента. Оно не подключает Telegram, Gmail, Calendar, Instagram или закупщик напрямую. Его задача — дать всем будущим интерфейсам и навыкам единые контракты памяти, задач, решений, подтверждений и аудита.

Рабочий результат v0:

- можно создать и прочитать профиль;
- можно сохранить проверенный факт в память;
- можно создать, изменить и завершить задачу;
- можно зафиксировать решение вместе с причиной;
- можно создать запрос на подтверждение и принять либо отклонить его;
- любое изменение оставляет запись в журнале действий;
- навык может подключаться только через формальный контракт и минимальные разрешения.

## 2. Границы первой версии

### Входит в v0

- локальный backend-модуль Arthur Core;
- PostgreSQL как рабочее хранилище;
- миграции базы данных;
- домены и права доступа;
- профиль пользователя;
- память;
- задачи и ожидания;
- журнал решений;
- подтверждения;
- аудит;
- реестр навыков;
- программный API для будущего Gateway;
- unit- и integration-тесты.

### Не входит в v0

- Telegram-бот;
- веб-интерфейс;
- LLM-оркестратор;
- Gmail и Google Calendar;
- n8n-сценарии;
- векторный поиск;
- голос;
- автоматические бронирования;
- запуск существующего закупщика;
- импорт всей исторической памяти.

## 3. Структура кода

Рекомендуемая структура:

```text
apps/arthur-core/
  server.js
  routes/
  middleware/
  tests/

agents/arthur-core/
  profile/
  memory/
  tasks/
  decisions/
  confirmations/
  audit/
  skills/
  shared/

data/arthur/
  migrations/
  seeds/

docs/arthur/
```

Arthur Core не должен зависеть от внутреннего кода Purchasing Agent. Взаимодействие с ним позже выполняется через адаптер навыка.

## 4. Домены данных

Обязательные домены первой версии:

- `personal`;
- `health`;
- `travel`;
- `content`;
- `business`;
- `purchasing`;
- `academy`;
- `finance`;
- `system`.

Каждая сущность, кроме системного аудита, должна иметь `domain`. Доступ между доменами запрещён по умолчанию.

## 5. Профиль

Профиль хранит стабильные настройки пользователя:

- идентификатор;
- имя;
- часовой пояс;
- локаль;
- предпочтительный канал;
- активность профиля;
- даты создания и изменения.

Произвольные предпочтения не добавляются колонками в основную таблицу. Для них используется структурированная память с типом `preference`.

## 6. Память

### Типы записей

- `fact` — подтверждённый факт;
- `preference` — предпочтение пользователя;
- `policy` — правило работы Артура;
- `project_state` — состояние проекта;
- `reference` — ссылка на внешний источник или артефакт.

### Обязательные поля

- `id`;
- `owner_id`;
- `domain`;
- `type`;
- `key`;
- `value_json`;
- `source_type`;
- `source_ref`;
- `confidence`;
- `valid_from`;
- `valid_to`;
- `status`;
- `created_at`;
- `updated_at`.

### Правила

- одинаковый ключ может иметь историю версий;
- новая истина не удаляет старую запись, а закрывает период её действия;
- активная запись должна быть однозначной внутри `owner_id + domain + key`;
- пароли, данные карт и одноразовые коды запрещены;
- чувствительность хранится отдельным уровнем: `normal`, `sensitive`, `restricted`.

## 7. Задачи и ожидания

### Статусы

- `new`;
- `planned`;
- `in_progress`;
- `waiting`;
- `needs_confirmation`;
- `done`;
- `cancelled`.

### Обязательные поля

- заголовок;
- описание;
- домен;
- приоритет;
- статус;
- срок;
- следующий шаг;
- причина ожидания;
- связанный человек или организация;
- источник;
- связанные сущности;
- даты создания и изменения.

Задача в статусе `waiting` обязана иметь `waiting_for` и дату следующей проверки. Задача не считается выполненной только потому, что сообщение или письмо отправлено.

## 8. Журнал решений

Решение хранит:

- формулировку решения;
- причину;
- рассмотренные альтернативы;
- автора;
- дату;
- связанные задачи и проекты;
- условия пересмотра;
- статус: `active`, `superseded`, `reversed`.

Новое решение не удаляет старое. Оно может заменить его через `supersedes_decision_id`.

## 9. Подтверждения

### Уровни риска

- `low` — безопасное обратимое действие;
- `medium` — внешнее действие без финансового списания;
- `high` — финансовое, юридическое, кадровое или необратимое действие.

### Статусы

- `pending`;
- `approved`;
- `rejected`;
- `expired`;
- `executed`;
- `failed`.

Запрос подтверждения содержит точное описание будущего действия, входные данные, риск, срок действия и идентификатор навыка. После одобрения нельзя незаметно изменить параметры действия: используется fingerprint полезной нагрузки.

## 10. Аудит

Все write-операции фиксируют:

- инициатора;
- тип инициатора: `user`, `system`, `skill`, `automation`;
- домен;
- действие;
- тип и идентификатор сущности;
- состояние до и после;
- корреляционный идентификатор;
- результат;
- ошибку;
- время.

Аудит append-only. Обычные модули не могут изменять или удалять записи аудита.

## 11. Контракт навыка

Каждый навык регистрируется с полями:

- `skill_id`;
- `name`;
- `version`;
- `status`;
- список разрешённых доменов;
- список разрешённых операций;
- декларация внешних действий;
- максимальный уровень действия без подтверждения;
- endpoint или локальный adapter;
- health status.

Минимальный программный контракт:

```js
{
  manifest: {
    skillId,
    name,
    version,
    domains,
    permissions,
    confirmationPolicy
  },
  async validate(input, context) {},
  async execute(input, context) {},
  async healthcheck() {}
}
```

Навык не получает прямой доступ ко всей базе. Он работает через сервисы Arthur Core либо ограниченный adapter context.

## 12. Внутренний API v0

Минимальные группы методов:

- `profile.get`, `profile.update`;
- `memory.list`, `memory.getActive`, `memory.upsertVersion`, `memory.archive`;
- `tasks.create`, `tasks.list`, `tasks.update`, `tasks.transition`;
- `decisions.create`, `decisions.list`, `decisions.supersede`;
- `confirmations.create`, `confirmations.approve`, `confirmations.reject`, `confirmations.markExecuted`;
- `skills.register`, `skills.list`, `skills.setStatus`;
- `audit.list` с ограниченными фильтрами.

HTTP API допускается, но бизнес-логика должна находиться в независимых сервисах, чтобы позже её могли использовать Telegram Gateway и n8n.

## 13. Безопасность

- secrets не хранятся в таблицах памяти;
- SQL-запросы только параметризованные;
- JSON проверяется схемами;
- write-доступ проверяется по домену и permission;
- high-risk действия требуют отдельного подтверждения;
- production и test базы разделены;
- миграции обратимы там, где это возможно;
- логирование не должно раскрывать restricted-данные.

## 14. Тесты приёмки

Arthur Core v0 считается готовым, если:

1. Миграции поднимают чистую test-базу.
2. Можно создать профиль и прочитать его.
3. Версионирование памяти сохраняет историю и одну активную запись.
4. Недопустимый переход статуса задачи отклоняется.
5. `waiting` без даты проверки отклоняется.
6. Решение можно заменить без удаления истории.
7. Подмена payload после подтверждения обнаруживается fingerprint-проверкой.
8. Навык без разрешения не читает чужой домен.
9. Каждая write-операция создаёт audit event.
10. Существующие тесты Purchasing Agent продолжают проходить без изменений.

## 15. Первый технический спринт

Первый кодовый спринт после утверждения спецификации:

- создать каркас `agents/arthur-core`;
- реализовать доменные константы и схемы валидации;
- подготовить PostgreSQL migrations для профиля, памяти и аудита;
- добавить test database setup;
- написать тесты миграций и базовых ограничений;
- не реализовывать Telegram, LLM и внешние навыки.

Это единственный допустимый объём первого кодового спринта Arthur Core.
