## Изменения кандидата

- Изолированный компонент с usePathname внутри Suspense с пустым fallback. Он не выводит зависимый от URL HTML. Начальный pathname записывается при init, учитывая порядок эффектов дочернего и родительского компонентов. Повтор того же пути, в том числе повтор эффекта StrictMode, пропускается. Последующие переходы отправляют `ym(id, 'hit', pathname)`. Query и fragment не отправляются; при выключенном счётчике просмотры не копятся.
- Начальная инициализация Метрики и содержимое ecommerce dataLayer сохранены.
- Только точное `NEXT_PUBLIC_METRICA_GOALS_ENABLED === 'true'` включает новые цели; по умолчанию они выключены. Существующие params продолжают работать независимо от этого флага.

| Событие | ID JavaScript-цели | Новые параметры цели |
| --- | --- | --- |
| add_to_cart | vz_add_to_cart | отсутствуют |
| begin_checkout | vz_begin_checkout | отсутствуют |
| submit_order | vz_submit_order | отсутствуют |
| trackPurchase из подтверждённого paid-пути | vz_paid_purchase | order_price: положительное конечное revenue, currency: RUB |

Обычный `trackEvent('purchase')` не вызывает цель оплаты. Для очереди trackPurchase сохраняет отдельную внутреннюю сумму. Произвольные параметры события не копируются в цели: request_id, transaction_id, контакты, имена, адреса и URL в новых goal payload отсутствуют. Существующий transaction_id в params и actionField.id в ecommerce не менялись. trackPurchase остаётся доверенной внутренней функцией: доказательство оплаты принадлежит существующему вызывающему коду, не самому API аналитики.

## Настройка в кабинете — только после доступа и согласования владельца

1. Авторизоваться в нужном аккаунте Метрики, подтвердить права редактирования и соответствие счётчика магазину. Не подменять ID и не считать текущую конфигурацию проверенной.
2. В настройках счётчика открыть «Цели», добавить четыре отдельные цели типа «JavaScript-событие» / «Целевое событие» (название зависит от интерфейса). Указать точные идентификаторы из таблицы, сохранить. Не использовать URL страницы успеха как доказательство оплаты.
3. В настройках счётчика включить «Электронная коммерция», указать контейнер `dataLayer`, сохранить. В коде уже используется это имя; не добавлять второй тег или второй поток purchase.
4. После явного согласования владельца включить `NEXT_PUBLIC_METRICA_GOALS_ENABLED=true` в согласованной сборке. Next.js встраивает NEXT_PUBLIC-переменные при сборке: простое изменение окружения уже собранного клиента недостаточно. В этом кандидате окружение и сборки не менялись. Для отключения — убрать флаг или задать false и пересобрать в отдельном согласованном релизе.
5. В разрешённом локальном/тестовом окружении с подменённым ym проверить вызовы и очередь без сети. После отдельного разрешения на проверку реального счётчика использовать отладку Метрики (`_ym_debug=1` в адресной строке), проверить события и отсутствие персональных данных в новых аргументах. Debug query не должен попадать в SPA hit. Первоначальный автоматический просмотр остаётся поведением существующего тега; эта работа не меняет его URL-политику.
6. В отчётах «Конверсии» проверить поступление каждой цели; в отчётах электронной коммерции — товары, покупки и выручку. Оплату проверять только на законном существующем серверном paid-пути; не создавать фиктивные оплаченные заказы и не вызывать ручной reachGoal оплаты в рабочем счётчике. Сверять с разрешёнными владельцем агрегатами, не выгружая клиентские данные. Отсутствие событий не доказывает отсутствие продаж: блокировщики и закрытие вкладки могут препятствовать отправке.

## План отчётности без вымышленных цифр

Выбрать период и единую модель атрибуции. В отчёте по поисковым системам выделить органический поиск Яндекса, затем страницы входа; отдельно `/collections/vozdooh-selection` (TOP25). Страница входа и последующее посещение коллекции — разные срезы; view_collection не является отдельной новой целью.

Для сегмента сравнивать визиты, посетителей, добавления в корзину, начало оформления, отправленные заявки и подтверждённые paid-покупки. Не выдавать число достижений целей за число уникальных заказов. Отдельно смотреть конверсию по каждой стадии, регионы, покупки/продажи и RUB-выручку из ecommerce. Доход paid-цели и ecommerce purchase описывают одну покупку — их нельзя складывать. Воронка в клиентской аналитике может быть неполной; это не бухгалтерский реестр. Исторические params не восстанавливают задним числом достижения новых целей.
