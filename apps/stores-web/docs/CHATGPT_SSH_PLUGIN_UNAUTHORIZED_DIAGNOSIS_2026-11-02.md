# Диагностика UNAUTHORIZED собственного SSH‑плагина ChatGPT «Управление серверами»

Дата: 2026-11-02. Источник задачи: GitHub issue #292. Статус: диагностический
отчёт + минимальные изменения‑кандидаты в этом репозитории (без публикации и
merge). Production, действующие туннели, авторизация и системные сервисы не
изменялись и не перезапускались.

## 1. Симптом и идентификаторы

- Ошибка на вызове `list_connections` из ChatGPT:
  `UNAUTHORIZED: this tunnel requires an active organization context.
  Configure the organization ID or send the OpenAI-Organization header.`
- Туннель `stores-web1` (ID `tunnel_6ab5bd7578e08191b254dd320fe3d237`) работает —
  процесс туннеля подключён, падения туннеля нет.
- Организация OpenAI Platform: `Miska`.
- ChatGPT workspace ID: `db5afd41-cf6d-429b-8606-618608f933e2`.
- App ID: `asdk_app_6adea525378c8191abec09d504487190`.

## 2. Ограничения sandbox (явно, по требованию задачи)

Проверка выполнялась в изолированном worker‑sandbox, и это принципиально
ограничивает глубину диагностики:

- Нет SSH и любого сетевого доступа к stores‑web1: исходники плагина, его
  манифест, env‑конфигурация, systemd‑юнит и логи недоступны.
- Нет доступа к кабинету OpenAI Platform (организация `Miska`) и к
  разработческому кабинету ChatGPT (app `asdk_app_…`, workspace
  `db5afd41-…`): история настроек, манифест и привязки туннеля со стороны
  OpenAI проверить отсюда нельзя.
- Заголовки, которые ChatGPT реально шлёт в туннель (в т.ч.
  `OpenAI-Organization`), видны только на стороне OpenAI/плагина.
- Ограничения не обходились: сеть вне package‑registry не использовалась,
  секреты и dotfiles не читались.

## 3. Что проверено в этом репозитории

Полнотекстовый поиск по всему worktree (идентификаторы туннеля/app/workspace,
`list_connections`, текст ошибки, `OpenAI-Organization`, org‑контекст) не нашёл
ни кода плагина, ни его манифеста/конфигурации, ни истории настроек. Плагин в
этом репозитории не версионируется.

По `compose.production.yml` продовый стек на stores‑web1 — это `caddy`,
`postgres`, `directus`, `web` (Next.js) и `onec-sync`. Сервиса плагина ChatGPT
в стеке нет: плагин «Управление серверами» работает на том же хосте вне этого
compose‑стека и управляется отдельно (systemd/отдельный контейнер — уточнить
на хосте).

Вывод по разделу: корень проблемы находится вне этого репозитория — на хосте
stores‑web1 (код/конфиг/окружение плагина) и/или в настройках OpenAI ChatGPT
(привязка app↔tunnel↔org/workspace). Отчёт даёт проверяемую причину в виде
ранжированных гипотез с дискриминирующими проверками, а не «подтверждённый
факт»: подтвердить единственную причину из sandbox невозможно (см. раздел 2).

## 4. Семантика ошибки

Сообщение — HTTP 401 от слоя, который терминирует запрос в туннель (edge
туннеля OpenAI либо сам плагин за туннелем; формулировка не позволяет различить
это без логов). Оно несёт две ветки исправления:

1. «Configure the organization ID» — на стороне сервера/приложения есть
   настраиваемый organization ID, который сейчас не задан или не совпадает.
2. «send the OpenAI-Organization header» — запрос пришёл без организационного
   контекста, который ожидал слой проверки.

Важно: туннель «работает» как транспорт (процесс подключён), а отказ — на
путь запроса «ChatGPT → edge OpenAI → туннель → плагин» для конкретного
вызова инструмента. То есть организационный контекст теряется либо не
подставляется platform‑стороной, либо не принимается/не настроен серверной
стороной.

## 5. Проверяемая причина (гипотезы, ранжировано)

### H1. Рассинхрон привязки org/workspace между app и туннелем (наиболее вероятно)

App `asdk_app_…` привязан к workspace `db5afd41-…`, туннель
`tunnel_6ab5bd75…` создан в организации `Miska`. Если app недавно
пересоздавался/переносился между workspace/org, либо туннель пересоздавался под
другим аккаунтом, platform при вызове инструмента может не передавать тот org
context, под который настроен туннель/плагин. Тогда каждый вызов
(`list_connections` — первый же инструмент) падает с 401, а сам транспорт
туннеля остаётся «зелёным». Согласуется с формулировкой «send the
OpenAI-Organization header».

Проверка/опровержение: сверить в кабинетах (1) к какой org привязан туннель,
(2) к какой org/workspace привязан app, (3) совпадают ли они и с organization
ID, настроенным в плагине. Несовпадение ⇒ подтверждено.

### H2. Плагин потерял organization ID в конфигурации после изменения/рестарта на хосте

Фраза «Configure the organization ID» указывает на серверную настройку. Если на
stores‑web1 плагин (пере)запускался с усечённым окружением (не подгружен env‑
файл, изменён systemd‑юнит, чистка конфигов), его собственная проверка org
контекста будет отвергать все вызовы, не доходя до `list_connections`. Туннель
при этом штатно держит соединение.

Проверка/опровержение: на хосте сравнить, задан ли organization ID в
конфигурации/окружении плагина, и сопоставить время первого сбоя с временем
последнего изменения/рестарта сервиса плагина.

### H3. Изменение platform‑стороны (регрессия/миграция заголовков)

Менее вероятно и из sandbox не проверяемо: изменение в передаче org‑заголовков
для workspace‑scoped apps со стороны OpenAI. Оставляем как остаточную
гипотезу; диагностика H1/H2 либо подтвердит одну из них, либо оставит H3.

## 6. Дискриминирующие проверки (read‑only, без рестартов)

Выполняет мейнтейнер. Ничего из этого не меняет production и не перезапускает
сервисы.

1. На stores‑web1: логи плагина в момент вызова `list_connections`.
   Ключевой факт — доходит ли запрос до процесса плагина:
   - в логе плагина есть входящий запрос, и 401 пишет плагин ⇒ серверная
     проверка (H2);
   - запроса в логе плагина нет, 401 возвращается раньше ⇒ edge/туннель
     (H1/H3).
2. На stores‑web1: конфигурация/окружение плагина — задан ли organization ID
   (имя переменной/ключа смотреть в коде плагина; значение не публиковать).
3. В кабинете OpenAI Platform (org `Miska`): к какой организации привязан
   туннель `tunnel_6ab5bd75…`.
4. В разработческом кабинете ChatGPT (app `asdk_app_…`, workspace
   `db5afd41-…`): какой туннель и org указаны в настройках app; есть ли в
   истории манифеста недавние изменения (перепривязка, смена URL туннеля).
5. Анонимный read‑only зонд конечной точки плагина из нового скрипта‑
   кандидата (раздел 7):
   `CHATGPT_PLUGIN_BASE_URL=<origin туннеля> npm run diagnose:chatgpt-plugin`.
   Вердикт `ORG_CONTEXT_REQUIRED` (exit 2) воспроизводит инцидент на discovery‑
   пути без участия ChatGPT и подтверждает, что guard срабатывает до
   выполнения инструментов; `REACHABLE` говорит, что guard не на discovery‑
   пути, и диагностика смещается на auth вызовов инструментов.

## 7. Минимальные изменения‑кандидаты (в этом репозитории, без публикации)

Код плагина здесь не живёт, поэтому кандидат — не «фикс плагина», а
инструмент воспроизведения/проверки гипотезы, не нарушающий ограничений:

- `scripts/diagnostics/chatgpt-plugin-checks.ts` — чистая классификация
  ответов (маркер org‑контекста, вердикты, exit codes).
- `scripts/diagnostics/chatgpt-plugin-org-context.ts` — read‑only CLI:
  только анонимные GET к discovery‑документам (`/`,
  `/.well-known/ai-plugin.json`, `/.well-known/apps.json`, `/openapi.json`);
  не шлёт `Authorization` и намеренно не шлёт `OpenAI-Organization` (guard
  должен быть наблюдаем без него); не вызывает инструменты (никакого
  `list_connections`, никаких POST); обрезает вывод; без `CHATGPT_PLUGIN_BASE_URL`
  отказывается работать.
- `tests/chatgpt-plugin-diagnostics.test.ts` — юнит‑тесты классификации
  (без сети).
- `package.json` — команда `npm run diagnose:chatgpt-plugin`.

## 8. Безопасный план восстановления (кандидат, выполняет мейнтейнер)

Каждый шаг обратим; единственный потенциальный рестарт — сервиса самого плагина
— только с явным одобрением и никогда web/directus/postgres/caddy и действующих
туннелей.

1. Зафиксировать текущие значения: org туннеля (каб. 3), org/workspace app
   (каб. 4), organization ID в конфиге плагина (пров. 2) — до любых изменений.
2. Если H1 подтверждён (несовпадение привязок): перепривязать app к туннелю
   правильной org/workspace настройкой в кабинете (конфиг‑only, без рестартов
   на хосте). Проверка: повторный вызов `list_connections` из ChatGPT.
3. Если H2 подтверждён (org ID не задан в плагине): восстановить значение в
   конфигурации/окружении плагина по первоисточнику (кабинет/документация),
   затем — с одобрения мейнтейнера — перезапустить только сервис плагина.
   Проверка: вызов `list_connections`, логи плагина.
4. После каждого шага: `npm run diagnose:chatgpt-plugin` (ожидаемый переход к
   `REACHABLE` либо снятие 401 на discovery‑пути) и ретест в ChatGPT.
5. Откат: вернуть исходные значения конфигурации/привязок из шага 1;
   состояние туннелей и системных сервисов при этом не затрагивается.

## 9. Чего не делать (по ограничениям задачи)

- Не менять production, действующие туннели, авторизацию и системные сервисы;
  не перезапускать их.
- Не публиковать ключи/секреты; в отчёте и логах — только идентификаторы из
  задачи.
- Не запускать Codex на stores‑web1; не использовать другие модели вместо Kimi.
- Sandbox‑ограничения (раздел 2) не обходить.
